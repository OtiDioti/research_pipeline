## Boundaries and required behavior

1. A claim use is an explicit, versioned binding of an exact candidate revision, exact target context, recorded support routes and their exact assessment revisions, and the relevant issue and policy references. It has a stable identity, a monotone eligibility generation and an auditable current reassessment status. Preserve the exact historical binding and every generation transition; do not mutate the claim statement, Review, Issue or old use snapshot. A use starts `requires_reassessment`/not eligible, unless a later separately authorized scientific disposition mechanism exists. Neither registration nor a favorable reported Review produces `eligible=true` or canonical scientific disposition.
2. Resolve only recorded dependencies, with bounded finite traversal and exact revision/kind checks. Each route is a conjunction of its pinned premises; alternatives remain separate. Review route outcomes and Issue affected-record links inform which recorded uses require reassessment, but an attributed Issue is not itself a verified refutation or scientific decision. Conservatively flag potentially material changes; never silently ignore a changed relevant assessment/issue because a statement revision is unchanged. Unrelated revisions must not invalidate unrelated uses merely because a global event count advanced.
3. In the same metadata transaction that accepts a new relevant Review or Issue revision, update all affected registered uses and their eligibility generations, or reject the entire submission without a partial record/head/receipt/event/eligibility effect. A concurrent read must see the prior complete state or the new complete state. No deferred worker, post-commit scan, cache-only marker or second independent commit may leave a stale favorable window. The Architect must specify how affected uses are indexed and how complete bounded propagation is enforced before accepting a write; resource exhaustion fails closed.
4. A changed support assessment, reopened/material Issue, or affected premise/route requires reassessment for recorded downstream uses. A route that remains unchanged can be recorded as a possible alternative, but it preserves positive eligibility only if an earlier authorized sufficiency assessment for that exact route, context and policy was already recorded. Such an authorization contract is not present in the accepted Review/Issue records. This request must therefore never infer positive scientific eligibility from an alternative edge or reported `sufficient` value. Historical old-context support remains historical; context transfer requires separate review.
5. Provide a bounded current inspection API that returns an exact coherent snapshot: use identity, generation, status/reasons, candidate/context, relevant assessment/issue pins, and unresolved limitations. Its output must distinguish mechanical freshness, attributed review content and authorized disposition. It must not expose a generic record as verified authority. Explicit current-status reads may use indexed metadata, but exact historical reads and original submission receipts retain their old meaning. No promotion/apply-disposition, author self-endorsement, human approval, worker admission, live execution, provider call or scientific truth inference is in scope.
6. Preserve supported existing stores, backups, restore, migration and historical generic/typed reads. If new metadata needs a schema version, provide an explicit opt-in version and verified forward migration/restore path; never silently reinterpret or rewrite old schema or receipts. Define behavior when older stores cannot expose this current view. No backend, dependency, validator, runtime prompt, administrative grant or frozen-run changes.

## Outcome and chosen boundary

Provide a bounded local API that refreshes an explicitly identified prior readable view to a newly captured committed snapshot while detecting and preserving direct human edits, renamed files, additions and deletions. A successful result identifies the old generation, the new complete generation and inspectable unsubmitted preservation evidence. It never silently adopts displayed edits into canonical records or changes committed scientific artifact paths.

Use **immutable successor generations**. Compare the prior tree against its independently pinned canonical plan, preserve observed divergent content and path/identity relationships, and publish a new complete reading generation at a caller-selected absent location. Retain the entire prior tree unchanged, including human renames and edits; do not replace, chmod, rename back, clean or repair it. Readers continue to pin concrete generations. The refresh result and a readable continuation report provide the explicit route to the successor and preserved proposed work. This is more than another materialize call: preservation/comparison and its complete association with the successor are required before refresh success.

Coordinator decision DEV-041: in-place multi-file replacement would make mixed generations and concurrent editor changes harder to recover; a mutable current-pointer manager adds a separate lifecycle that existing interfaces do not need. Immutable successor publication consumes the accepted generation contract and preserves historical paths. A current convenience pointer, full runtime vault manager and CLI are subsequent obligations, not silently completed here. This choice is an internal engineering decision, not human scientific approval.

At most two independently acceptable milestones: (1) bounded read-only divergence capture, exact detached identity/path diagnostics and preservation planning; (2) safe preservation/successor publication, offline inspection/recovery and a complete exercised example. Each milestone must pass the frozen full-suite and complete-diff checks. The Architect prescribes concrete public signatures, strict versioned representations, limits, failure boundaries and tests before the Writer implements. Only the delegated CWI Writer changes product source; no recursive CWI or implementation in the original checkout.

## Required behavior and acceptance criteria

### AC-01 — Explicit inputs and reproducible comparison (R-004/R-026/R-028)

Require an explicit prior view location and independent expected plan identity/canonical plan, a new accepted ReadablePlan derived through the existing snapshot API, caller-selected output location(s), source/protected roots and finite count/byte allowances. Do not trust a modified manifest, generated YAML, filename or arbitrary provenance dictionary to supply authority or an expected base. The new snapshot must refer to the same project identity; explicit changes in selection/current revisions remain visible, never an accidental cross-project refresh. The API must work with already detached plans without rereading live record heads during publication. Keep captured/proposed/committed and expected/observed byte identities separate. Define same-plan no-op behavior explicitly and test it.

Capture one bounded, internally consistent observation of the prior tree through pinned no-follow descriptors and stable file/directory bindings. Compare every expected generated/artifact file against its saved exact hash/size/path; report mode-only changes separately. Bound expected and unexpected files/directories, per-file and total bytes, metadata/diagnostics and traversal before unbounded reads or recursion. Include safe extra subtrees so a renamed directory is not silently omitted. Refuse unsafe or inaccessible entries, concurrent modifications and resource/I/O failure rather than returning a successful partial preservation. The old view and canonical store remain unchanged on every path. A missing/corrupt/changed control manifest is a conflict unless the explicitly supplied independent canonical plan can safely establish the original inventory; never infer a base from suspect content.

### AC-02 — Honest rename and identity handling (R-027/R-028)

Retain the old canonical logical path, observed path, expected and observed hashes, record/revision/artifact identity where actually established, and original mapping/provenance. Support unambiguous unchanged file and directory renames using exact byte identities and old manifest relationships. Identical bytes may have multiple logical owners: preserve all associations or diagnose ambiguity instead of guessing. A rename combined with content edits must be preserved even when identity cannot be inferred; an explicit validated caller mapping or an unresolved identity diagnostic is acceptable. Titles, embedded properties and coincidental text are data, never authenticated identity. New, missing, type-changed, conflicting and portable-alias paths must have explicit deterministic outcomes. No deletion or rename is interpreted as a canonical revision or instruction to remove evidence.

### AC-03 — Preserve proposed work before refresh success (R-019/R-028)

Preserve independent exact copies of all safe divergent content, including modified generated pages, modified copied scientific artifacts, renamed/added files and their meaningful relative organization, plus a bounded machine-readable manifest and readable explanation. Record deletions/missing targets without inventing bytes. Preserve the prior expected manifest/identity separately from any observed control-file bytes. The preservation artifact is explicitly **unsubmitted proposed work**, not canonical research, endorsed status or a replacement for the original source. Exact existing canonical bytes and the entire prior tree remain intact. Use explicit private permissions, no writable hard links, no symlink traversal, no plugin/config activation and no interpretation/execution of supplied text, code, notebooks, TeX or PDFs.

Provide a concrete documented route from a preserved edited work-product file to an editable checkout and the existing preview/explicit expected-base import API. Reuse those interfaces; do not implement an automatic canonical importer. Generated status/index edits require an explicit authored proposal and cannot change a scientific disposition or operating policy. Ambiguous identities stay preserved for manual mapping. Demonstrate a stale canonical base conflict while both the edited bytes and historical revision survive. No discard/delete operation is needed in this slice.

### AC-04 — Complete successor and links (R-026/R-027/R-031)

Build the new reading view only from the new canonical plan. Unmodified generated views refresh to the new committed values; edited display text cannot leak into the new canonical projection. New generated relative links and headings pass the existing plan verifier. Old frozen authored bundles are never rewritten to follow human renames. The refresh report must explain missing/moved/ambiguous targets from the prior generated inventory and direct the reader to the corresponding preserved path or unresolved diagnosis. Distinguish generated links that are mechanically verified from arbitrary authored Markdown/wikilinks that are not certified; declare those limits rather than claiming all authored links were repaired. Retain old-to-new exact record mappings, including records omitted by a changed selection and historical revisions still referenced.

### AC-05 — Publication, conflicts and recovery (R-019/R-026/R-028/R-092)

Use private preparation and exclusive complete publication, with a coherent manifest binding the prior identity, captured differences/preservation and successor plan. The Architect may choose an atomically published refresh package containing the concrete generation and preservation, or a guarded staged protocol whose final complete marker is published only after both independent outputs are durably verified. Specify which directory is opened as the successor vault and how readers pin it. Do not advertise a refresh as complete while preservation or the new generation is incomplete. Reuse proven no-replace same-parent publication and existing guarded filesystem helpers where appropriate; do not weaken them. All supplied output locations must be absent and disjoint from prior view, source, canonical storage, backups and controller/protected roots.

A concurrent edit after initial comparison must be detected at the final binding/byte checks, causing a clear conflict with all work retained. State the existing same-owner/privileged mutation trust limit honestly; no new universal editor lock is promised. Competing publishers cannot overwrite each other or unrelated files. No automatic cleanup, overwrite retry, rollback of visible output or blind replay after uncertain acknowledgment. Persist bounded intent/readiness/publication observations sufficient for offline inspection to distinguish incomplete preparation, complete unpublished output, completed publication with lost acknowledgment, competing destination, and inconsistent evidence. Interrupted operations remain inspectable and a caller can identify the exact complete successor if publication occurred; a real I/O failure must not become ordinary successful divergence. Historical fsync acknowledgment cannot be invented from current file presence.

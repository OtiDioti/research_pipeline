## Required data and behavior

1. General envelope: validated stable opaque record identity, positive integer revision (reject boolean), stable record kind, immutable JSON-compatible content and attributed creation provenance. Initial supported kinds cover research context, claim, justification, evidence and task specification. These are storage envelopes; do not claim every scientific payload field/remaining §5.1 kind is implemented. JSON content is untrusted descriptive data, never authority. Defensively isolate caller/returned mutable data from committed history.
2. Explicit typed exact record references include identity and revision, with relationship labels; artifact references include validated SHA-256 digest and size, never arbitrary paths. References resolve to committed revisions or members of the same atomic batch. Reject dangling, malformed and wrong-kind references where a kind is declared. Historical references must never drift to the latest revision.
3. Keep task operational status and claim scientific disposition separate. Controller-supplied operational state is recorded, not proof of execution. Initial scientific claim submissions are provisional only; reject attempts to encode a canonical supported/endorsed disposition. A completed task can coexist with a provisional claim and conveys no scientific support. This is not an implementation of assessment/eligibility policy.
4. Artifact put accepts bytes through the trusted controller API and publishes by SHA-256 under an owned object area using private staging and durable atomic publication. Existing identical content is safely reused; mismatched bytes/size, corrupted destinations, symlinks/nonregular objects and malformed digests fail without overwriting canonical bytes. Verify content on read and before committing links. Document actual filesystem/durability assumptions; no claim of protection from a hostile storage owner. Read-only object permissions plus controlled access and integrity checks are required. No automatic destructive orphan cleanup or external download fallback.
5. SQLite metadata uses explicit schema version 1, foreign-key enforcement and durable settings, with bounded locking behavior. Reopen an existing store without recreating or erasing it. Reject unknown/malformed schema versions without mutation. General migration paths/backups remain explicit later obligations. Use serialized write transactions and relevant per-record expected-head checks, not a global event timestamp that rejects unrelated updates.
6. A submission carries stable submission identity, actor/provenance, a batch of new revisions, exact links/artifacts and expected current heads (zero/absent identity for creation). One revision per identity per batch; a new revision is the expected current head plus one and preserves kind. All identity/head checks, record/relation/artifact registrations, durable receipt and attributed audit event commit in one transaction. No in-place scientific revision rewrite or deletion. Querying exact history and current heads after restart yields the same committed values.
7. Idempotency is durable: canonicalize JSON mapping order and reject unsupported/nonfinite JSON values. Define fingerprint semantics explicitly, including meaningful ordered lists and request actor/expectations. Exact retry of a previously committed submission returns the original receipt, even if a record head later advanced; it adds no record or audit event. Same ID with conflicting content/actor/expectations fails atomically. Check recorded idempotency before treating that exact retry as a stale new write. Do not claim duplicate resource charging is implemented when this slice has no ledger.
8. Publish artifact bytes before the metadata transaction may refer to them. If the transaction or process fails, no committed result may reference unstored bytes and no partial batch/event may appear. Unreferenced immutable objects may remain and are explicitly harmless retained orphans. Reconcile uncertain acknowledgment by submission ID, not blind replay with a fresh ID. Detect later missing/corrupt referenced artifacts when exposing a supposedly intact result; do not report successful evidence availability from metadata alone.
9. Two independently opened store connections must reject stale writes on the relevant record. A failed write preserves existing revisions, heads, relations, events and submission identities. Unrelated-record updates do not force conflicts. This is local transactional safety, not a distributed queue or full attempt-fencing implementation.
